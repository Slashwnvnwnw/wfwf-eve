## 三、各接口改动详情与实现方式

### 接口1：采样待办的指标结果编辑服务整改

**接口路径：** `qua/web/rest/ebg/update-todo-qua-indicator`
**修改类型：** 接口修订-一般

#### 改动了什么

1. **附件由单个改为最多 10 个**
  
  - 入参 `fileId`（Long）删除，改为 `fields`（`List<Long>`），并加 `@SizeValidation(max = 10)` 限制附件数量不超过 10。
  - 对应 BO `TodoTaskQuaIndicatorUpdateBo` 的 `fileId` 字段同步改为 `List<Long> fields`。
2. **新增"是否涉及"字段**
  
  - 入参新增 `isInvolve`（必填，`@NotNullValidation` + `@RegexpValidation(FLAG_REGEX)`，0-涉及 / 1-不涉及）。
  - 指标分类结果表 `t_ebg_samp_task_indicator_result` 新增三个字段：`is_cse`、`is_ccr`、`is_pse`。
  - BO `EbgSampTaskIndicatorResultBo` 新增 `isCse`/`isCcr`/`isPse` 三个字段。
3. **"是否涉及"与考核责任人联动校验**
  
  - 新增 `validateAssessorByInvolve(req)`：当 `isInvolve = 0`（涉及）时，当前指标维度的考核责任人（CSE/CCR/PSE 之一）必填，否则抛 `PARAM_ERROR`；不涉及则非必填。
4. **根据界面选择的是否涉及填充对应字段值**
  
  - 在 `setAssessorByDict(req)` 中，根据责任人类型（`assessorType`）将 `isInvolve` 写入对应的 `isCse`/`isCcr`/`isPse` 字段（0-涉及，1-不涉及）。
5. **附件绑定逻辑改造（支持多文件）**
  
  - `handleAttachment` 由单文件改为遍历 `fields` 列表，逐个校验附件存在性并更新 `file_status = 1`（被关联），同时根据操作类型（初审/申诉/复审/关闭）设置上传环节。

#### 实现方式

- **分层实现**：Controller（入参校验）→ Service（`SampToDoServiceImpl.updateTodoTaskQuaIndicator`）→ DAO → Mapper XML。
- **字段落库**：`EbgSampTaskIndicatorResultMapper.xml` 的 `update` 语句新增 `is_cse`/`is_ccr`/`is_pse` 的动态 `<if>` 更新与 ResultMap 映射。
- **责任人联动**：`setAssessorByDict` 通过字典 `ECARE_INDICATORS_KEY` 解析指标责任人类型，再按类型回填对应是否涉及字段。
- **校验顺序**：先 `setAssessorByDict` 确定责任人类型，再 `validateAssessorByInvolve` 校验必填。

### 接口3：采样待办详情的附件列表查询服务整改

**接口路径：** `qua/web/rest/ebg/samp-task/attachment/query`
**修改类型：** 接口修订-简单

#### 改动了什么

- 出参新增"是否可以删除"标记 `isDeletable`（0-可以 / 1-不可以）。
- 实现删除权限判断逻辑。

#### 实现方式

- **VO 层**：`EbgSampTaskTodoAttachmentVo` 新增 `isDeletable` 字段。
- **Service 层**：`getAttachmentQuery` 中：
  - 获取当前登录人 `userAccount`、当前问题所处环节 `checkStatus`、是否管理员 `isAdmin`。
  - 对每个附件调用 `isDeletable(attachment, checkStatus, userAccount, isAdmin)` 计算删除标记。
- **权限规则**（`isDeletable` 方法）：
  1. 模块管理员/系统管理员 → 可删除（返回 "0"）。
  2. 附件的上传环节与当前问题所处环节一致，且登录人为上传人 → 可删除（返回 "0"）。
  3. 其余情况 → 不可删除（返回 "1"）。
- **环节匹配**（`isStageMatchCurrentStatus`）：将上传环节中文（初审/申诉/复审/关闭）映射到 `checkStatus` 枚举值（待初审/待申诉/待复审/完成）进行比对。

### 接口4：采样待办详情的附件删除服务

**接口路径：** `qua/web/rest/ebg/samp-task/attachment/delete`
**修改类型：** 新增/修改/删除类接口-简单

#### 改动了什么

- 新增删除接口，入参 `fileId`（文件标识）、`todoId`（待办标识），均必填。
- 逻辑删除附件记录（`file_status = 2`）。
- 同步删除 EDM 平台存储的文件。

#### 实现方式

- **入参 BO**：新增 `DeleteEbgSampTaskTodoAttachmentReqBo`，含 `fileId`、`todoId` 两个 `@NotNullValidation` 字段。
- **常量**：`EbgConstants` 新增 `FILE_DELETED_STATUS = 2`（文件状态-已删除）。
- **Controller**：新增 `POST /attachment/delete` 端点，使用 `@UsLog` 记录操作日志（moduleName/objectType/operationName=DELETE/paramsIndex/resultChecker），调用 Service 后返回 `Result.success()`。
- **Service 接口**：`EbgSampTaskTodoService` 新增 `deleteAttachment` 方法声明。
- **Service 实现**（`EbgSampTaskTodoServiceImpl.deleteAttachment`）完整流程：
  1. **查询附件**：`selectById(fileId)`，不存在抛 `FILE_ID_NOT_EXIST`。
  2. **归属校验**：附件 `todoId` 与入参 `todoId` 不一致抛 `PARAM_ERROR`。
  3. **已删除校验**：`file_status = 2` 抛 `FILE_DELETED`（重复删除拦截）。
  4. **权限校验**：复用接口3的 `isDeletable` 逻辑，无权限抛 `NOT_OPERATE_PERMISSION`。
  5. **逻辑删除**：将附件 `file_status` 置为 `2`，执行 `updateTaskTodoAttachment`。
  6. **删除 EDM 文件**：调用 `deleteEdmDoc(edmDocId)` 删除 EDM 平台存储的文件。

#### EDM 删除的健壮性处理（重点）

- **事务边界**：`deleteAttachment` **不加 `@Transactional`**，避免"数据库事务内执行网络 IO"导致连接池耗尽/事务超时。本地逻辑删除（单条 update）由 MyBatis 自动提交，先释放数据库连接，再执行 EDM 远程删除。
- **失败隔离**：EDM 删除封装在 `deleteEdmDoc` 私有方法中，`try/catch` 捕获异常仅记录日志、不抛出，保证"本地逻辑删除成功"是最终结果，EDM 清理为 best-effort，避免远程失败导致接口 500 与本地状态不一致。
- **空值保护**：`edmDocId` 为空时跳过 EDM 删除并记录 warn 日志。
- **初始化**：调用 `edmClientUtil.initIam()` 初始化 EDM 客户端（`edmService` 字段）后再 `deleteDoc(docId, "system")`，避免 NPE。

## 四、可以优化的点

### 接口1（指标结果编辑）

1. **附件绑定与指标更新的事务一致性**：当前 `handleAttachment` 与指标更新是否在同一事务内需确认。若分属不同事务，附件绑定失败可能导致指标已更新但附件未关联，建议评估是否需要统一事务边界。
2. **`fields` 列表去重**：入参 `fields` 未做去重，同一 `fileId` 重复传入会重复执行 update，可加 `distinct` 或 `Set` 去重。
3. **批量更新优化**：当前遍历 `fields` 逐个 `updateTaskTodoAttachment`，可改为批量 `update` 减少数据库交互。

### 接口3（附件列表查询）

4. **`isDeletable` 中管理员分支被注释**：当前代码中管理员判断分支被注释掉（`/* ... */`），实际只按"上传环节一致 + 上传人"判断。若需求要求管理员可删除，应恢复该分支（接口4 中已恢复）。需与产品确认最终权限口径。

### 接口4（附件删除）

5. **EDM 删除的最终一致性**：当前 EDM 删除失败仅记日志，可能导致"数据库已删除但 EDM 文件残留"。可引入**重试机制**或**异步消息队列**（RocketMQ/Kafka）补偿，保证最终一致。
6. **EDM 删除失败的可观测性**：建议增加失败告警/监控，便于及时发现 EDM 残留文件。
7. **`deleteDoc` 的 accountId 硬编码**：当前固定传 `"system"`，可考虑从 `UserSessionUtil.getSession().getUserAccount()` 获取真实操作人，便于审计追溯。

### 通用

8. **事务与远程调用解耦**：接口4 已通过"去 `@Transactional` + 失败隔离"处理，但更规范的做法是拆分为"本地事务方法 + 独立远程调用方法"，或使用事务同步器（`TransactionSynchronization`）在事务提交后触发远程调用。
9. **代码复用**：接口3 与接口4 的权限判断逻辑（`isDeletable`/`isStageMatchCurrentStatus`）可抽取为公共工具类，避免两处重复实现。
