简约版
针对政企质检列表查询中循环内逐条调用客户组织名称与白名单接口导致的 N+1 查询瓶颈，重构为循环前批量查询 + 内存 Map/Set 缓存，消除循环内数据库 IO，显著降低接口响应耗时

普通版
优化政企质检列表查询的 N+1 查询瓶颈：原实现中 forEach 循环内对每条记录分别调用 getAccountByNumber 和 countBySiteNetworkId 查询客户组织名称与白名单状态，重构为循环前一次性批量查询并缓存至内存 Map/Set，循环内直接取值，消除循环内数据库 IO，提升列表接口性能

复杂版
定位并优化政企质检列表查询的 N+1 查询瓶颈：原 getTaskList 在 forEach 循环内对每条记录分别执行客户组织名称查询（getAccountByNumber）与白名单校验（countBySiteNetworkId），数据量大时产生大量重复数据库 IO

重构为循环前批量查询方案：新增 buildAccountNameMap（批量查询客户组织名称构建 Map 缓存）与 buildWhitelistedAccountSet（批量查询白名单构建 Set 缓存），循环内从内存直接取值，将 N+1 次查询降为 2 次批量查询

同步处理超大函数门禁告警：将 account 相关代码拆分为独立私有方法，getTaskList 由 64 行降至 39 行、getTaskDetail 由 54 行降至 48 行，通过 CodeCheck 超大函数门禁

带背景和解决方案的版本
背景：政企质检列表接口在数据量增长后响应变慢，检视发现 getTaskList 的 forEach 循环内对每条记录分别调用 getAccountByNumber（客户组织名称）和 countBySiteNetworkId（白名单校验），构成典型的 N+1 查询瓶颈，产生大量重复数据库 IO

解决方案：将循环内逐条查询重构为循环前批量查询——新增 buildAccountNameMap 批量获取客户组织名称构建 Map 缓存、buildWhitelistedAccountSet 批量查询白名单构建 Set 缓存，循环内直接从内存取值，将 N+1 次查询降为 2 次批量查询；同时拆分超大函数，getTaskList 由 64 行降至 39 行、getTaskDetail 由 54 行降至 48 行，通过 CodeCheck 超大函数门禁

效果：消除循环内数据库 IO，显著降低列表接口响应耗时，提升大数据量场景下的查询性能
